# Dependency decisions

The runtime now declares ten direct crates: `serde_json`, `url`, `tokio`, `bytes`, `hyper`, `hyper-util`, `http-body-util`, `rustls`, `tokio-rustls` and `webpki-roots`. Each was already in the locked dependency graph; removing Reqwest reduces the all-platform lockfile from 133 packages to 86 without adding a package/version. Direct dependencies expose the maintained HTTP parser's header/buffer controls and the verified TLS stream so our small policy wrapper can count bytes before parsing/decryption. HTTP/TLS/URL parsers and cryptography remain library responsibilities; request policy, byte/time budgets and redaction remain project code. Only required runtime/HTTP1/TLS features are enabled, with Ring explicitly selected as the crypto provider. The same built-in WebPKI roots and operator-owned extra CA policy are retained. No regex engine, HTML parser, proxy middleware or database is introduced.

The server still needs dependency review and advisory gates before a stable release. The lower-level HTTP transport must preserve the pinned DNS behavior, TLS hostname checks, disabled ambient proxies, redirect policy, and bounded streaming reads.

`serde_json` enables its `arbitrary_precision` feature so response syntax validation accepts valid large JSON numbers (for example `1e400`) without forcing them into finite floating-point values. The existing nesting guard and response byte cap remain active. This feature adds no crate to the dependency graph.

## Candidate inventory and notices

Linux x86_64 candidate archives now contain `dependency-inventory.json` and `third-party/` notice files. Packaging runs `cargo metadata --locked --offline --filter-platform x86_64-unknown-linux-gnu` inside the committed source snapshot after the build, then walks the resolved normal/build dependency graph. Development-only edges and the root project are excluded. The inventory records each crate’s name, version, reported license expression, registry source, locked SHA-256, resolved features and notice filenames. It contains no Cargo-cache or workspace paths. This is our versioned inventory format, not a claim of SPDX/CycloneDX schema conformance or an exact list of linked binary symbols.

For every included crate, packaging hashes the cached `.crate` archive against `Cargo.lock` and compares shipped license/copying/notice files with the archive bytes. Notice symlinks, out-of-crate paths, oversized files, missing notices/license metadata and unsupported non-registry sources stop packaging for review. The Cargo registry source and archive cache must be available; this step performs no network fetch. Notice files remain unchanged. The inventory includes build dependencies, which may not be linked into the executable.

The initial target inventory contains 107 crates and 181 notices. Standard-library Python tests (`python3 -m unittest discover -s tests -p 'test_*.py'`) cover path-free output, notice preservation, modified-notice rejection and modified-archive rejection. CI runs these tests before packaging. Future dependency changes may change counts; CI must regenerate and verify the inventory.

The project remains GPL-3.0-or-later; dependency license expressions are reported separately. This inventory is evidence for dependency/notice review, not a license-compatibility decision, vulnerability scan, signature verification, or complete dependency source bundle. The human release review must still evaluate distribution obligations and the remaining supply-chain gates before a stable release.

After the bounded HTTP/1 transport migration, the Linux target inventory contains 71 crates, down from the initial 107. The all-platform lockfile contains 86 packages including the root, down from 133. No package/version was added. Counts describe different scopes and are not interchangeable.

Development client probes retain SDK 1.32.1 for legacy compatibility and pin `@modelcontextprotocol/client` 2.3.1 for modern requests. Dependency review rejected the initial 2.0.0 development pin because of [OAuth issuer binding](https://github.com/advisories/GHSA-6qxp-vccf-f47h) and [cross-origin HTTP redirects](https://github.com/advisories/GHSA-6prh-2h8m-c8cw) advisories. The stdio-only probe does not use those affected HTTP/OAuth paths, but the pin was updated without a gate exemption. `npm audit --audit-level=low` reports zero vulnerabilities for the locked development graph after the update. These JavaScript packages do not enter the Rust server or its runtime inventory.

The CLI Inspector pin is also updated to 2.11.0, whose declared client dependency is 2.3.1, replacing 2.5.0’s 2.0.0 pin. Probe invocations disable npm install scripts and use only the prebuilt stdio CLI. Historical Inspector 2.5.0 behavior is retained only as historical evidence, not the current tested pin.

## TLS advisory correction and full-lock gate — 2026-10-22

A fresh cargo-audit0.22.2 scan found two published advisories in the previously tested lockfile: [RUSTSEC-2026-0382](https://rustsec.org/advisories/RUSTSEC-2026-0382.html) affected `rustls-webpki`0.103.15, and [RUSTSEC-2026-0381](https://rustsec.org/advisories/RUSTSEC-2026-0381.html) affected `webpki-roots`1.0.9. Both concern distrusted emSign intermediate certificate paths (CVE-2026-111943). The lockfile now resolves patched0.103.16 and1.0.10 respectively; the direct root dependency also requires at least1.0.10. No runtime crate or feature was added. Older experimental artifacts must be rebuilt; a valid signature authenticates bytes, not absence of newly disclosed vulnerabilities.

The local before/after scan used RustSec database commit `59ef7abf8ce56ea80fe7eba97ba3835449009fa4`: two findings before, zero vulnerabilities/warnings after. This is an advisory match and dependency correction, not an independent exploit reproduction. Existing controlled TLS/SNI/extra-CA tests must still pass for the changed executable. Prior native-client observations identify older artifacts and do not automatically certify this build.

CI now installs development-only cargo-audit0.22.2 with its locked tool dependencies, fetches a fresh official RustSec checkout, records its Git identity and tool version, and audits the **entire** Cargo.lock without target filters or ignored advisories. `--deny warnings` fails informational warnings as well as vulnerability findings. Fetch/audit failures block the gate; trusted-main provenance signing also requires this job. The report and database identity are retained as a seven-day CI artifact. Dependency-review on changed packages remains useful but did not replace this full-lock scan.

The command deliberately uses `--no-yanked`: registry yank status is not checked by this gate. There is no claim of a complete source-code audit, npm/Inspector audit, license approval or perpetual dependency safety. Rerun with a fresh database before release, and review newly disclosed findings rather than adding silent exemptions. Ordinary server users do not need cargo-audit or an advisory database.

## Locked development SDK advisory gate

CI now also queries npm advisories for `tools/mcp-sdk-probe/package-lock.json` before trusted-main signing. The separate job uses `--package-lock-only`, explicitly includes development/optional/peer classes, disables scripts and performs no dependency installation. Findings at low severity or higher fail npm; the following response check additionally requires the supported complete report shape and zero total findings. Network/service/report errors fail the job rather than being interpreted as a clean audit. Signing requires this job as well as the full-lock RustSec scan and independent rebuild.

The report, Node/npm versions and SDK lockfile SHA-256 are retained as a seven-day artifact. Local verification on2026-10-22 used Node22.20.0/npm11.19.1 and reported zero findings; this observation expires as advisory data changes. No ignore or automatic fix is applied, and no runtime crate or JavaScript dependency is added.

That original report covered only the **locked SDK probe graph**. The subsequent locked-Inspector gate below extends coverage to a separate Inspector lockfile; neither report covers the Rust server or installed native clients. Neither audit is a code review, license decision or guarantee that a package is safe. Recheck the relevant graph before release and keep toolchain/advisory identities with candidate evidence.

## Locked Inspector installation and advisory coverage

The development Inspector now has its own `tools/mcp-inspector-probe/package.json` and integrity-bearing lockfile, pinning the existing official2.11.0 CLI and resolved transitives. Install with `npm ci --prefix tools/mcp-inspector-probe --ignore-scripts --no-audit --no-fund`. The smoke runner verifies the installed top-level version and invokes the local CLI directly. Missing installation fails with setup instructions; it never falls back to `npx` or performs package resolution during a probe. Node/npm are development smoke prerequisites, not Rust-server runtime dependencies. Installed node_modules are ignored and excluded from committed source exports/skill packages.

CI installs this lockfile with scripts disabled for both primary and independent candidate probes. The advisory job now has separate SDK and Inspector matrix entries, each auditing its complete lockfile without installation, requiring a zero-total complete response, and retaining graph/tool identity. Both entries must pass before signing. This closes the earlier on-demand Inspector transitive-resolution gap; it does not audit native clients or prove source-code/credential safety. No Rust crate was added and no server behavior changed.

Local locked Inspector audit reports zero findings. Full legacy/auto/modern CLI checks pass, including a replay with a node-only PATH (no npm/npx available) and an unreachable registry configuration. This verifies that the already installed smoke path does not require package-manager invocation; it is not a claim of a general process network sandbox or proof that every library is network-free.
